# 0004 — Initial protocol encoding and communication bindings

- **Status:** Accepted for the 0.1.0-draft design
- **Date:** 2026-11-05
- **Decision owners:** Project maintainers

## Context

Independent implementations need a common representation and precise validation rules. The project needs separate contracts for controller-to-adapter communication and operator/client-to-controller management. The protocol should be implementable with common libraries across languages and should not select an implementation language.

## Decision

The 0.1.0-draft protocol adopts the following initial standards and bindings:

| Concern | Selection | Scope |
|---|---|---|
| Interchange representation | JSON, RFC 8259 | Protocol objects and examples |
| Structural schemas | JSON Schema Draft 2020-12 | Requests, responses, descriptors, configuration and test fixtures |
| Timestamps | RFC 3339 date-time | Protocol instants, serialized as UTC where generated by an implementation |
| Canonical request fingerprints | RFC 8785 JSON Canonicalization Scheme | Only where deterministic JSON hashing/signing is required |
| Adapter RPC semantics | JSON-RPC 2.0 | Adapter request/response semantics |
| Initial optional adapter process binding | `jsonrpc-stdio-v1` | UTF-8, newline-delimited JSON on stdin/stdout |
| Management API description | OpenAPI 3.2.1 | HTTP/JSON client API |

These choices are distinct from the controller's implementation language, database, process framework, or deployment packaging.

## Compatibility and validation rules

- Schema files identify JSON Schema Draft 2020-12 with the standard `$schema` URI.
- Protocol version and schema revision are distinct.
- Validators MUST enforce protocol-specific timestamp and URI constraints; implementations MUST NOT assume JSON Schema `format` annotations are assertions unless assertion behavior is enabled or equivalent validation is performed.
- Duplicate JSON object property names are rejected.
- The JSON-RPC process profile requires string request IDs and one message per line.
- Large binary data is transferred outside JSON-RPC messages.
- The management API is asynchronous for mutating operations and returns durable operation resources.
- Canonicalization is used for deterministic fingerprints only when required; ordinary wire JSON does not need to be canonicalized.

## Rationale

The selected standards have broad language support, are independently specified, and keep the protocol readable and testable. JSON Schema provides portable structural validation; OpenAPI supports independent HTTP clients; JSON-RPC defines an established request/response envelope without forcing the project to adopt a particular network transport.

## Consequences

- Schemas, examples, and test vectors must be committed to the repository.
- A language-neutral conformance suite must verify schema and behavioral rules.
- The adapter process binding is an optional implementation profile, not a requirement for in-process adapters.
- A future remote adapter transport requires its own reviewed binding specification.
- These are draft protocol choices. They may be revised before a stable 1.0 release if interoperability testing reveals material problems.
