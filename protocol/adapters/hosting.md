# Hosting Adapter Contract

**Status:** Draft, version 0.21.0-draft.

## 1. Responsibility

The hosting adapter turns provider-neutral infrastructure requests into provider API calls. It handles provider-specific APIs and IDs, polls asynchronous work, and normalizes provider errors.

It does not install a game, decide whether a backup is safe, route players, or own lifecycle policy.

## 2. Capability names

An adapter may declare any subset of these capabilities:

| Capability | Meaning |
|---|---|
| `hosting.regions.list` | List regions |
| `hosting.plans.list` | List instance plans |
| `hosting.os_offerings.list` | List OS offerings and versions |
| `hosting.instance.create` | Create from a validated specification |
| `hosting.instance.find_by_resource_key` | Find an instance by its exact controller-owned create key |
| `hosting.instance.inspect` | Inspect one exact instance |
| `hosting.instance.start` | Start a stopped instance |
| `hosting.instance.stop` | Stop an instance |
| `hosting.instance.reboot` | Reboot an instance |
| `hosting.instance.destroy` | Destroy an instance |
| `hosting.instance.wait` | Wait/poll for a defined provider outcome |
| `hosting.network.inspect` | Inspect addresses and network attachments |
| `hosting.firewall.manage` | Manage firewall policy when explicitly supported |
| `hosting.bootstrap.deliver` | Deliver or invoke a protected bootstrap reference |
| `hosting.bootstrap.inspect` | Inspect one exact bootstrap execution |

Each capability declares constraints, permission scopes, idempotency behavior, and whether the adapter can reconcile a lost response. Catalog listings are read-only. Return region, plan, and OS IDs unchanged; they are opaque. An `unknown` availability result never authorizes creation.

The read-only region, plan, and OS-list capabilities use registered schemas with opaque page tokens. The adapter-level `hosting.instance.create` call uses [instance-create-input.schema.json](../schemas/hosting/instance-create-input.schema.json) and [instance-create-output.schema.json](../schemas/hosting/instance-create-output.schema.json). Every controller-managed create carries a stable `resource_key` generated by the controller; the provider adapter MUST persist it as searchable provider metadata and make repeated create requests with that key idempotent. The broader [provision request](../schemas/hosting/provision-request.schema.json) belongs to controller orchestration and is not sent wholesale to the hosting adapter.

If a create response is lost, `hosting.instance.find_by_resource_key` uses [instance-find-by-resource-key-input.schema.json](../schemas/hosting/instance-find-by-resource-key-input.schema.json) and [instance-find-by-resource-key-output.schema.json](../schemas/hosting/instance-find-by-resource-key-output.schema.json). The adapter MUST complete all required provider pagination before reporting matches and MUST return at most two matches, enough to distinguish zero, exactly one, and duplicates. One exact match can reconcile the create. Zero matches do not prove the request never took effect, so the controller MUST NOT retry solely on that result. Multiple matches require operator review and MUST NOT be adopted automatically.

`hosting.bootstrap.deliver` accepts [bootstrap-deliver-input.schema.json](../schemas/hosting/bootstrap-deliver-input.schema.json) and returns [bootstrap-execution-output.schema.json](../schemas/hosting/bootstrap-execution-output.schema.json). It MUST bind the exact instance, immutable revision, and SHA-256 digest. The controller supplies only non-secret inputs; credentials remain in the protected secret-resolution channel. An accepted or uncertain execution MUST retain its exact `bootstrap_execution_ref` so the controller can reconcile it with `hosting.bootstrap.inspect`, whose input is [bootstrap-inspect-input.schema.json](../schemas/hosting/bootstrap-inspect-input.schema.json) and whose output uses the same execution schema. The adapter MUST reject an execution reference associated with another instance or bootstrap revision.

## 3. Create specification

A create request SHOULD include:

- Logical server and environment IDs.
- A stable controller-generated resource key that is searchable after a lost response.
- Region and plan IDs scoped to this adapter.
- Provider OS offering ID, plus readable distribution, version, and architecture.
- Hostname and non-secret labels.
- SSH public-key references.
- Network and firewall-policy references.
- Protected bootstrap reference, immutable revision, integrity digest, and non-secret inputs.
- Minimum resources and requested expiry/retention policy, where applicable.

Provider-native plan, region, and OS IDs are opaque strings. The protocol does not assume providers share catalog names.

A request MUST NOT contain raw API tokens, passwords, private keys, storage credentials, or game-player data. Do not smuggle secrets in cloud-init/user-data or provider metadata. The only exception is the single-use SSH host key in section 6.1, under every condition listed there.

## 4. Operations and outcomes

- **Create:** Return a provider-operation reference and, when available, an instance reference. Do not report the instance active until you observe that postcondition.
- **Inspect:** Report the exact target identity, normalized state, available region/plan/OS facts, network observations, and observation time. Bind the result to the requested instance. `unknown` does not mean `active` or `destroyed`.
- **Start, stop, reboot:** Use exact-instance schemas. A completed start or reboot confirms `active`; a completed stop confirms `stopped`. An `accepted` result needs a provider-operation reference and does not prove completion. If the result is unknown, inspect the exact instance before retrying. A completed reboot does not prove game readiness. Before a normal reboot of an instance with persistent data, or unknown data status, the core must obtain a confirmed game save or clean stop bound to that instance. Bypassing this requires separate emergency approval bound to `hosting.instance.reboot.emergency` and the exact instance; unsaved changes may be lost. If a result names the wrong instance, treat it as untrusted and inspect before retrying or starting dependent work.
- **Destroy:** Use an exact-instance input and typed result. Before dispatch, the core confirms authorization, stopped state, a verified backup for the current data generation, and the destruction plan. Any required approval binds the exact destroy action, logical server, environment, adapter, instance, plan fingerprint, approver, and expiry. An expired or mismatched approval blocks the provider call. `accepted` requires a provider-operation reference and is not confirmation; `unknown` requires exact-instance inspection before retry.
- **Wait:** Bind the request to one exact instance and expected state. Include a provider-operation reference when available; otherwise poll the exact instance until the expected state or a terminal result is observed. Any returned provider-operation reference must belong to that instance's adapter and environment. The bounded timeout does not cancel provider work. `pending` stays pending; `succeeded` confirms the action only when the exact expected state is observed. `unknown`, terminal `failed`, or mismatched references require inspection before retry.

The adapter MUST support lookup/inspection sufficient to reconcile create and destroy results. If it cannot, the core suspends uncertain operations for operator action.

## 5. Instance references and security

An instance reference contains adapter ID, environment ID, resource kind, and opaque provider ID. Never use a provider ID from one environment as a target in another.

Use least-privilege provider credentials; never include them in diagnostics. Network and firewall changes are privileged operations and need separate capabilities and authorization.

### 5.1 Billing increments

A hosting adapter for a provider that bills instances in fixed increments SHOULD declare the increment as the descriptor constraint `billing_increment_seconds` (3600 for hourly billing). The core uses it to time scale-up and scale-down so a running instance is used for the time already charged; see the scaling policy in [the core design](../../docs/CORE_DESIGN.md#billing-aware-scaling). The constraint is advisory: it never authorizes destroying an instance, and every destroy still requires the verified backup and approval rules in [the operation catalog](../operation-catalog.md).

## 6. Bootstrap

The initial preferred path uses a provider-supported standard OS image and a reviewed, versioned bootstrap. The adapter may deliver a protected script reference or start a separate bootstrap runner. A repeated delivery with the same instance, revision, digest, and operation step MUST be idempotent or return the exact existing execution reference; it MUST NOT launch an untracked duplicate run. The controller reconciles an accepted or uncertain execution by inspecting that exact reference rather than resubmitting blindly.

Report how bootstrap started, its immutable revision/digest, execution reference, exit status, timestamps, and validation evidence. A successful script exit does not prove the game is installed or ready. The controller MUST perform separate host and game readiness checks before transitioning the logical server to `ready`. Uploading a script or submitting a remote command does not prove the host is prepared.

### 6.1 Verifying a new instance's SSH host key

Before the controller sends any secret to a new instance over SSH, such as storage credentials for a restore, it MUST verify the instance's SSH host key against a key the controller chose. Trusting the first key an address presents is not enough: until the controller has a verified key, anyone answering at that address could receive the secret.

To make that possible, the create request MAY carry exactly one **single-use ed25519 SSH host key** in cloud-init user data. This is the only secret a create request may carry, and only when every condition below holds:

1. **Fresh and unstored.** The key is generated for that one create and never reused. The controller does not store the private half. It stores the public half durably, in the same transaction that claims the create for dispatch, so the stored key is always the one actually sent.
2. **Exact target only.** The controller connects only to the address the provider reports for that exact instance. It accepts only the stored single-use key with the `ssh-ed25519` algorithm, and only before the handoff expires (24 hours after creation unless configured otherwise).
3. **A swap-only first login.** The first connection uses an account that can run one forced command and nothing else: no shell, terminal, forwarding, or file transfer. That command generates a new ed25519 host key on the instance, removes the single-use key and cloud-init's copies of the user data, reloads the SSH server, prints only the new public key, and removes the account. It refuses to run a second time.
4. **Pin the new key.** The controller accepts the printed key only if it is one well-formed `ssh-ed25519` public key that differs from the single-use key. From then on it uses only this pinned key, and the single-use key is never accepted again.
5. **Replace the provider copy.** After pinning, the controller replaces the instance's user data at the provider. If the provider does not allow that, the handoff record says the expired key remains in provider metadata.
6. **Secrets last.** No secret is sent before the new key is pinned, and a secret is sent only on a connection whose host key is the pinned key.
7. **Mismatch is a hard stop.** A presented host key that does not match the expected key is never accepted. The controller sends nothing and does not continue until an operator investigates.

Where the provider offers a firewall that applies before the instance boots, the create request SHOULD attach one that admits SSH only from the controller's address. The instance's own firewall SHOULD do the same from its first configuration, so SSH is never reachable from other addresses.

Who can read the single-use key: the provider, anyone holding the provider account's API token, and processes on the instance itself through the provider's metadata service. All of them can already control the instance, so the key gives them nothing new. It does not cross the network in the clear, and it stops working minutes after first boot.

The handoff steps and their outcomes are checked by [hosting-bootstrap-host-key-handoff.json](../conformance/test-vectors/hosting-bootstrap-host-key-handoff.json).

## 7. Conformance cases

Test filtered catalog results, opaque pagination, unknown availability, exact-instance start/stop completion, accepted and unknown outcomes, create success and ambiguous timeout, pinned bootstrap delivery, duplicate delivery idempotency, bootstrap execution reconciliation, cross-instance execution mismatch, false bootstrap success, duplicate idempotency keys, inspect scope mismatch, provider transient failures, destroy-target mismatch, missing core authorization, and destroy-result reconciliation.
